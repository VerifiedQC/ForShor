A map of the Lean proofs for ForShor

VerifiedQC · October 2026

ForShor is a Lean 4 development that verifies Shor's order-finding algorithm from end to end. An implementation built on Toom-Cook multiplication is compiled from a high-level gate language down to a low-level abstract machine, and the compiled circuit is proved both correct — it returns the multiplicative order with probability at least κ / (log₂ N)⁴, κ ≈ 0.0548 — and cheap: for every ε > 0 there is a Toom-Cook arity at which it uses O(n^(2+ε)) elementary gates, n the size of the modulus register. The development is about 150 Lean files and 2,600 declarations spread over nine folders, which is more than anyone wants to read top to bottom. This site is a map of it.

The map is an interactive dependency graph of the repository. Each node is a folder or a .lean file; each arrow is an import. You can descend from the top-level folders to individual files, read every declaration with its docstring, jump to the source on GitHub, and see what each piece uses and is used by. It is meant to answer questions such as “where is Shor_correct stated, and what does it rest on?” without cloning the repository. The mathematics and the design decisions are described in our paper, ForShor: Formal Verification of Shor's Algorithm in Lean 4 with Verified Resource Estimation (Suresh, Patel, Cao and Tao, 2026); the paper tells the story and the map shows where each step of it lives in the code.

How to use the map

Nodes. Every box is a folder or a file. In the top view the colour of a folder is its role, as the legend in the lower left says: Framework is the specification every theorem is stated in; PhaseProduct, QFT and ModularExponentiation are the three subroutines, each verified on its own; Shor assembles them; GateCount counts the result; Reference turns a concrete Toom-Cook table into an executable circuit; Shared is a lemma library that every subroutine uses and that is not a step of the argument. Inside a folder the colours switch to layers — Math, Definitions, Spec, Proofs, Main — which is how each folder is organised. A folder shows how many children it has; a file shows its line count.

Arrows. An arrow is an import, drawn from the file that is used to the file that uses it, so reading a view left to right follows the proof. Not every import is drawn. A solid coloured arrow with a label is one we chose because the named theorem crosses it — the label is the theorem, and the right-hand pane lists these “curated arrows” for the view. A thin grey arrow is real structure that is not part of the story. A dashed arrow is an import from Shared. The toolbar button All imports overlays everything that was left out, and Focus on dims everything unrelated to the current selection, which is the quickest way to see what a single file depends on.

Moving around. Click a folder to descend into its own graph; the tree on the left and the breadcrumb at the top go back up, and Top returns to the first view. Click a node to open it on the right: its docstring, its declarations grouped by kind, and a link to the file on GitHub. The search box finds declarations, files and folders by name and jumps to them. The address bar follows the view and the selection, so any state of the map can be linked to, for example navigator.html#/Shor/Proofs?sel=…Correctness.lean.

The graph is generated from the source: scripts/gen_docs_graph.py reads the import lines, docstrings and declarations of every Lean file and every folder's README.md. The few arrows drawn per view are chosen by hand in docs/data/annotations.js and checked against the generated graph, so a renamed file or a dropped import fails the check rather than silently going stale.

Where to start

  • Shor_correct, the success-probability bound for the ideal circuit, and Shor_correct_approx_lowered, the same bound after compilation at the precision shorPrecision N, where half of it survives.
  • exists_shorGateCountBound, the O(n^(2+ε)) gate count, stated as an honest count of LowGate operations under an explicit cost model, and shorGateCountBound_of_setup, the same bound at its own exponent for any admissible Toom-Cook table.
  • Framework, if you want to know what the statements mean before reading the proofs: the registers, the gate languages, the semantics, the cost model and the correctness contract.
  • Reference, the computable instance: it lowers to an executable circuit, and lake exe forshor_emit prints it as JSON.

Checking it yourself

The project pins Lean v4.28.0 and a fixed Mathlib revision, so the prebuilt cache applies. With elan installed: 

lake exe cache get               # prebuilt Mathlib oleans
lake build                       # the whole development
lake exe forshor_emit 2 2 15 0   # the reference circuit for (k, a, N, m), as JSON

No proof uses sorry; the one occurrence in the repository is a test that the axiom audit rejects it. #print axioms on the headline theorems reports only propext, Classical.choice and Quot.sound, and decidable side conditions are closed by decide +kernel, never native_decide. The construction is generic in its Toom-Cook table: any table passing four decidable side conditions inherits the correctness theorem and the gate-count bound at its own exponent; the README's Submitting a table explains how such a table is stated and checked.
