A map of the Lean proofs for ForShor

What is actually proved about Shor's algorithm here, and where to find it in the code

VerifiedQC · October 2026

Feasibility of a quantum algorithm is typically argued using gate counts as the primary metric. In the case of factoring a 2048-bit modulus to break RSA, Shor's algorithm for order-finding is exceedingly popular, being taught in most introductory quantum computing courses and has an often-quoted gate count to evidence its practicality. Every instance of a gate count is an estimate coming from a cost model, a circuit design in a paper, or a spreadsheet explicitly accounting for each subroutine. ForShor develops the estimation from formally stated theorems, being a Lean 4 repository proving that a specific, fully compiled order-finding circuit is correct. It also proves the asymptotic gate scaling to be O(n^(2+ε)) elementary gates when substituting fast-multiplication from Kahanamoku-Meyer and Yao (2024) into the modular exponentiation subroutine. By using high-level gate languages mapping to low-level abstractions, both proofs can be checked in the same kernel, with no sorry<\code> and no axioms beyond Lean's own three.#print axioms on the headline theorems reports only propext, Classical.choice and Quot.sound. Decidable side conditions are closed by decide +kernel, never native_decide. The one sorry in the repository is a test that the axiom audit rejects it.

When treated independently, verifying correctness for an idealized circuit is not hard, nor is estimating the cost of a realistic circuit. Coupling these two actions is critically important as the world looks toward a fault-tolerant future, ensuring the resource bound and the correctness proof consider the same quantum algorithm. This way, a circuit with a bounded success probability has its gates explicitly counted, maximizing clarity and confidence as quantum algorithms like Shor’s order-finding, giving efficient solutions to classically hard problems, come into the scope of realizability.

Here, we will describe Shor’s order-finding algorithm as it is written in Lean. We detail the stepwise process from modulus to solution using quantum algorithmic subroutines, with interactive displays to allow the reader to freely traverse the argument. By pairing the proof in words to the Lean code, we aim to build a mathematical foundation both for Lean experts and for those who may be new to formal verification. Interactive nodes in the graphs below link back to the Lean code in the GitHub repository, letting a researcher easily locate where statements are proven.

We start with three theorems. Shor_correct says the ideal order-finding circuit, after classical continued-fraction post-processing, returns exactly the order r with probability at least κ / log(log₂ N + 1), that is Ω(1 / log log N).κ = 1/π² ≈ 0.101: Shor's per-numerator Fourier constant 4/π² times the 1/4 of the totient bound φ(r)/r ≥ 1/(4 · log(log₂ N + 1)). The exponent register has log₂(2N²) bits, the modulus register log₂(2N). The classical budget T bounds the convergent scan and costs no gates. This is the probability of getting r itself, not of landing in a good window. Shor_correct_approx_lowered says the same bound survives compilation, up to a factor of two, once the per-step precision η is set by a closed form in N.The lowering itself is exact; the only loss is the modular-exponentiation approximation. Holding it to half the ideal bound costs O(log n) extra work bits; at 2048 bits η ≈ 2⁻⁵³, about 105 extra work bits. shorPrecision is a closed form, so there is no existential constant a circuit builder would have to guess. Finally, exists_shorGateCountBound says that for every ε > 0 there is a Toom-Cook arity k at which the compiled circuit uses at most C · n^(2+ε) gates, n the size of the modulus register. That count is derived from LowGate operations under an explicitly stated cost model, containing common primitives like ripple-carry addition and bit-shifting.shorOrderFindingGateCount is LowGate.gateCount shorGateCostModel of the compiled circuit, and shorGateRate ε n is just n^(2+ε). A companion theorem, shorGateCountBound_of_setup, gives any admissible Toom-Cook table the bound at its own exponent log(2k−1)/log k; a k = 2 table runs at about n^2.585. Both theorems are about one table used at every width, which is the right statement for an exponent and not a gate count at n = 2048.

Shor's algorithm, as stated in Lean

Before the folders, the algorithm. Shor's algorithm is mostly classical. To factor N, pick a random base a; find the order r of a modulo N; and if r is even and a^(r/2) is not −1, then gcd(a^(r/2) ± 1, N) is a factor. Only the middle step, order finding, needs a quantum computer, and even there the quantum part is a single circuit of four steps followed by a measurement. Everything after the measurement is a classical continued-fraction scan.Every block is a definition or theorem in the repository; click it to see the Lean source, verbatim, with a link to the line. The blue row is orderFindingIdeal, the circuit the correctness theorem is about. The circuit that is compiled and counted has the same four steps, with the verified approximate modular exponentiation in third place. The whole loop is one theorem, Shor_end_to_end_factoring: at least half of the bases are good, and for each good one the circuit and the scan return r with probability at least κ / log(log₂ N + 1), after which the gcd step gives a factor.

Nearly all the gates are in one block, y ← aˣ mod N. That block is where the next diagram starts: it is built from QFT arithmetic, the QFT from phase products, and the phase product is where the fast multiplication lives.

The proof, layer by layer

The whole development is five layers deep, and they are best read top to bottom, which is also the order the proof goes in. The specification comes first: the vocabulary every statement is written in, and the contract the final object has to meet. Then the three subroutines, each verified on its own and each resting on the one before it. Then the assembly that proves Shor's algorithm correct. Then the cost of that assembled circuit, as a theorem. And finally the concrete instance that fills in every remaining choice and hands the framework the object it asked for.Every arrow is a real import between these folders, read from the Lean sources. The solid labelled arrows are the ones that carry the argument, and the label is the theorem or the vocabulary that crosses it; thin grey arrows are real structure that is not part of the story; the dashed ones come from Shared, a lemma library that is not a step. Inside PhaseProduct: one table, applied recursively

The layer graph says which folder rests on which. It does not say how the most expensive block is built, so here it is. A phase product applies exp(i·φ·x·z) to two n-bit registers. Doing it directly costs about n² gates. ForShor instead does what Toom-Cook does for integer multiplication: split x and z into k chunks, evaluate both chunk polynomials at 2k − 1 points, take one smaller phase product per point, and recurse. Everything about that scheme is fixed by one small table.

The table is a straight-line program on k registers, each holding a combination of the chunks. It may add a shifted copy of one register to another, negate, and shift, and at chosen moments it takes a phase product of whatever a register then holds.Every box in the figure is clickable: the parameters, each U, each of the five products, the levels, the base case and the output each open a panel with the Lean source. The register contents shown are computed by running the table, not typed in. The program type is Prog k, a list of valid_ops k: addScaled, negate, shiftL, shiftR, phaseProduct. A point is Point, where frac 0 is the point at infinity. The table drawn is one admissible k = 3 table, chosen because it reads well; the reference table in refOps uses the points genInterpolationPoints 3 = 0, −1, 1, −2, 2 on a single register. A table is admissible when the points are distinct, each phase product sees exactly the chunk polynomial evaluated at the next point, and the program ends where it started, so the registers are returned clean. These are four decidable conditions, checked by the kernel; nothing else about the table is trusted.

One level is the middle panel. At k = 3 the operations U₀ put x₀, x₀ + x₁ + x₂ and x₂ into the three registers, the values at 0, 1 and ∞; three phase products are taken; U₁ turns the registers into the values at −2 and −1 for two more; and U₂ undoes everything. Five phase products on chunks of a third of the width replace one on the full width.The phases of the five products are not the product's own: the angle for each point is an interpolation coefficient, so that the five phases multiply out to exp(i·φ·x·z). That is the algebra in PhaseProduct/Math, and lowerSignedPhaseProduct_correct is the theorem that the lowered circuit is correct for any admissible table.

The recursion is the right panel. Each of the five is again a phase product, lowered with the same table, until the width stops shrinking; at that point the circuit uses the naive phase product. The width at the next level is about a k-th of the current one, plus a constant number of padding bits, and the register arithmetic at a node is linear in its width. Summing over the tree gives O(n^(log_k(2k − 1))) gates: n^1.585 at k = 2, n^1.465 at k = 3, approaching n as k grows.The recursion is Policy.signedPlanOf, which recurses only while nextSignedWidth is smaller than the input width, so it terminates by construction. The three facts the count needs are prog_balanced_nextSignedWidth (next width at most ⌈w/k⌉ + c), phaseProgramOverhead_linear (overhead at most A·w + B) and balanced_phaseProduct_recurrence_solution; the exponent is phaseProductExponent k and the bound is PhaseProductGateCountBound. Modular exponentiation is a sequence of O(n) modular multiplications built on top of this, which is where the n^(2+ε) of the headline theorem comes from.

What this site is

The proof is about 160 Lean files and 2,700 declarations in eight folders, which is more than anyone wants to read top to bottom. This page is a guide to it. The layer graph above is the outline: each block is a top-level folder, each arrow is an import between folders, and opening a block shows what that folder is for, what it rests on and what it feeds, and its key statements quoted from the source with a link to the file and line on GitHub. It is meant to answer questions like “where is Shor_correct stated, and what does it rest on?” without cloning the repository.

The mathematics and the design are in our paper, ForShor: Formal Verification of Shor's Algorithm in Lean 4 with Verified Resource Estimation (Suresh, Patel, Cao and Tao, 2026). The paper tells the story, and the layer graph is its outline in the code.The arrows are the imports between top-level folders, read from the Lean sources by scripts/gen_docs_graph.py. The quoted statements are verbatim copies of the declarations at the file and line shown.

Where to start. Shor_correct and Shor_correct_approx_lowered for correctness; exists_shorGateCountBound for the gate count; Framework if you want to know what the statements mean before reading the proofs; and Reference for the computable instance, the one lake exe forshor_emit prints as JSON.

Checking it yourself

The project pins Lean v4.36.0-rc1 and a fixed Mathlib revision, so the prebuilt cache applies. With elan installed: 

lake exe cache get               # prebuilt Mathlib oleans
lake build                       # the whole development
lake exe forshor_emit 2 2 15 0   # the reference circuit for (k, a, N, m), as JSON

The construction is generic in its Toom-Cook table: any table that passes four decidable side conditions inherits the correctness theorem and the gate-count bound at its own exponent. The README's Submitting a table explains how such a table is stated and checked.
