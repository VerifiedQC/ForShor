ForShor

Shor's algorithm, verified in Lean 4 — gate count included

What ForShor is

ForShor is a formal verification of Shor's order-finding algorithm in Lean 4, together with a verified estimate of how many gates the circuit uses. It verifies an implementation of order finding built on fast Toom-Cook multiplication, from a high-level gate language down to a low-level abstract machine. This page is an interactive map of that proof; the code lives in the VerifiedQC/ForShor repository.

What is proved

  • Correctness. Shor_correct: the ideal order-finding circuit, after classical continued-fraction post-processing, returns exactly the order with probability at least κ / (log₂ N)⁴, with κ = 4e⁻²/π² ≈ 0.0548. Shor_correct_approx_lowered: the same bound survives compilation to the low-level machine, up to a factor of two, once the per-step precision is chosen as a closed-form function of N.
  • Resource estimate. exists_shorGateCountBound: for every ε > 0 there is a table arity k for which the fully compiled circuit uses O(n^(2+ε)) elementary gates, where n is the modulus register size. The count is an honest count of low-level gate operations under an explicit cost model, not an abstract measure. shorGateCountBound_of_setup gives any admissible submitted table the bound at its own exponent.
  • Trust base. No proof uses sorry (the one occurrence is a deliberate test that the axiom audit rejects it). #print axioms on the headline theorems reports only propext, Classical.choice and Quot.sound. The reference implementation is fully computable end to end and prints its circuit as JSON.

The challenge

The verified construction exposes exactly one degree of freedom: the Toom-Cook table (an arithmetic program over k limb registers plus its interpolation points), or a cascade of such tables indexed by operand width. A submission is a table plus four side conditions C1–C4, all decided in the Lean kernel (decide +kernel, never native_decide, enforced by an axiom check). Passing them is admissibility: the correctness theorem is proved once, generically in the table, so a submission needs no proof of its own. Everything else — the quantum construction, its proof, the precision, the trial count — is fixed and shared by every entrant.

How to read this map

  • Each view is one folder of the proof. Left to right is dependency order: a column is a dependency rank, and arrows point from what is used to what uses it. The spine runs Framework (the specification) → PhaseProduct, QFT, ModularExponentiation (three independently verified subroutines) → Shor (the assembly) → GateCount (the score) → Reference (the concrete, executable instance). Shared is a lemma library, not a step.
  • Click a folder to descend into its own graph, down to individual .lean files; click a node to see its declarations and docstrings on the right, with the GitHub link, and what it uses and is used by in the side strips. The tree on the left and the breadcrumb go back up.
  • Only the edges that tell the story are drawn by default; All imports overlays every import edge. Focus dims everything unrelated to the selection. Search finds any declaration, file or folder. Colours in the legend are roles (framework, subroutine, assembly, resource, submission, support).
