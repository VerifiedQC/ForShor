A map of the proofs for exact table optimization

The classical, theoretical companion to ForShor's PhaseProduct benchmark

Scope: read this first

This page is about a classical optimization problem, not a quantum circuit. Nothing in ForShor's verified order-finding circuit, its correctness theorem or its gate-count theorem depends on anything here, and no Lean file on either side imports the other. The two live in separate Lake projects with different toolchains.

The word PhaseProduct means two related things. In ForShor it is a lowered, verified quantum subroutine. Here, PhaseProduct/ is the optimization model of the table that drives it: a shift/add program with per-operation costs, and the question of which such program is cheapest.

ForShor's fast multiplication is driven by a table: for a Toom-Cook-style split with arity \(k\), a list of interpolation points together with a program of additions, shifts and negations that carries out the interpolation. ForShor verifies that any table passing four decidable side conditions yields a correct circuit with a gate-count bound. It does not say which table is best. Choosing one is the table-optimization problem posed by the paper and by ShorTableOptimization: for a target \((\text{mode},k)\) a policy chooses a point list, an order and a program; a contract checks them; and the structural score \(S = A + 5L\) counts arithmetic operations \(A\) and parallel phase-product layers \(L\).The score is arithmeticOperationCount + 5 * parallelPhaseProductLayerCount from the benchmark’s leaderboard/config.json. T-count is a different, downstream objective and is not what is shown NP-hard anywhere below.

This package answers two questions about that problem. What is the exact optimum? A Lean library, Library, models tables and their recursive cost and proves an optimizer optimal, and an exact Fortran solver (not formalized) computes the optima. How hard is it? A second, separate Lean project, Hardness, proves the sparsity barriers that make NP-hardness of the paper's own problem unlikely, and proves NP-hardness of a nearby problem in which the points are part of the input.

The package is more than the proofs. It also ships the paper, the prose research notes, the scripts that audit and map the Lean, an exact Fortran solver, and its independent tests, and says for each what kind of evidence it is: a kernel-checked theorem, a prose proof, or a program checked by replay.

What is not claimed

  • No NP-hardness of T-count. NP-hardness is shown only for the structural score with points supplied as input. It is not shown for T-count optimization, in general or for the Kahanamoku-Meyer–Yao (KMY) points, and the paper's fixed-points problem stays barrier-blocked.
  • The barriers are conditional. They say that an NP-hardness proof would imply P = NP. They are not hardness results and they do not show membership in P.
  • No running-time theorem. The optimality theorems are statements for each fixed \((K,W,N)\). Polynomial-time synthesis of optimal tables is not proved; for growing arity it is open. composition is arithmetic over hypotheses.
  • The solver is not formalized. The Fortran solver and its outputs are reproducible from the repository but are not Lean statements; Alignment/ relates its search windows to the Lean model.
  • Four research packages are prose. The thresholds, outer planner, profiles and normalization arguments the paper cites ship as prose proofs with review records in proof_notes/. They were reviewed by AI reviewers and are not machine-checked.

The exact solver

What it computes. Given a root width \(n\) and a largest arity \(K\), the solver returns the cheapest recursion for ForShor's PhaseProduct: which arity to use at each level, the literal table at each arity (the actual list of shift, add and negate instructions), and the total cost under the repository's cost model. It prints STATUS OPTIMAL only after replaying every table it reports. It solves PhaseProduct only; PhaseTripleProduct is not part of this application. It has no time, node or state budget: it finishes, or it stops with an ERROR, and an error is never an infeasibility or an optimality certificate.

How. There are three stages, which the figure shows from the top down: the decision for one table, the thresholds, and the outer optimizer. First, for one arity and one charge cap, an exact search decides whether a legal table exists and returns it (Oracle). Second, for each arity, bisection over the cap with a proved saturation ceiling finds the thresholds and the charge plateaus (Threshold). Third, the outer stage enumerates arity sequences with one integer offset per distinct arity and turns terminal integrality, width contraction, profile intervals and the exact objective into bounded integer linear constraints, which Kannan's algorithm solves exactly (Outer, Ilp, Lattice), over exact rationals (Rational) and saturating cost arithmetic (Arithmetic). Click a block for the procedures and the tests that exercise it.

What is claimed about the cost. These are the solver README's statements, which rest on the prose proofs in proof_notes/, not on Lean. The local threshold bound is \(2^{O(k^4\log(k+1))}\,\mathrm{poly}(\log n)\). The supplied-catalogue outer stage is separately polynomial in the numerical input width and the catalogue encoding, and the full route has \(2^{O(K^4\log(K+1))}\,\mathrm{poly}(n)\) complexity in the ideal exact-arithmetic model. Lean checks only the arithmetic of composing such bounds from hypotheses (RuntimeComposition.composition), including Kannan's theorem taken as a contract; there is no Lean running-time theorem about the algorithm.The README adds a caution worth repeating: the vertex-rounding preprocessing contributes \(m^{O(t)}\) to a generic bounded integer program, and only for this outer family (\(m=O(\log U)\), \(t!\le U\), with \(U\) the root-stop cost) is that polynomial in \(U\). Generic polynomial dependence on the number of constraint rows is not claimed.

How the answers are checked. Inside the program, every table is padded to its literal form and replayed by an independent routine before printing. Outside it, the tests recompute things in Python without sharing code with the Fortran:

The solver README is careful about what these show: the fixtures are finite, and the catalogue tests “establish outer correctness, not unrestricted physical table optimality by themselves”. The Fortran replay, the tests' Python replay and the Lean legality predicate are three separate implementations of the same rules; no theorem ties the solver's replay to the Lean predicate.

Reproducible numbers. Costs are the reproducible part; timings depend on hardware. From REPRODUCING.md: \(n=6,\ K=3\) gives cost 1476, \(n=40,\ K=5\) gives 92750, and \(n=60,\ K=3\) gives 200311. (We re-ran all three for this page; they match.) At \(n=2048\) the exact optimum at arity three or higher is not known; that is the question the ForShor challenge poses.

What is known about complexity

Two questions are easy to blur. What does the exact algorithm cost, and how hard is the problem? The paper answers the first with an upper bound, and the Lean library answers the second only in part. What the exact algorithm costs

The algorithm of the previous section is justified by an upper bound, \(2^{O(K^4\log K)}\cdot\mathrm{poly}(n)\) for largest arity \(K\) and root width \(n\). Every arrow that leads to that bound passes through prose. What Lean checks is the ceiling, the exact optimality and the profile transfer at the top, and an arithmetic lemma that composes bounds it is handed as hypotheses.

Read the figure this way. The \(27k^3\) charge ceiling is a Lean theorem, without hypotheses. Exact optimality is a Lean theorem for each fixed \((K,W,N)\), obtained from an exhaustive provider: it shows the optimum exists and is attained, and says nothing about running time. The profile transfer is Lean; that every table has a three-integer profile is prose. Saturation, the integer-program reduction, the local bound and the headline bound are prose or paper statements; Lean holds ingredients (small_integer_point, the separation criteria) that no other Lean file imports. The one Lean theorem that has the shape of a running time, composition, derives its bound from hypotheses that nothing verifies, so it is arithmetic and not a runtime theorem. The bound is fixed-parameter in \(K\); it is not uniform polynomial time.

How hard the problem is: the sparsity barriers

Lean proves that NP-hardness of the benchmark's table problem would collapse P and NP. The argument is Mahaney's: the optimum is at most \(B(k)=15k(2k-1)\), so with \(k\) in unary the yes-instances form a sparse set, and a sparse NP-hard set implies \(\mathrm P=\mathrm{NP}\). The two barriers differ in what they need. The first has no hypotheses and is for the structural score with the policy choosing its own points. The second is for a unary-parameter optimization language and needs a polynomial bound on the optimum as a hypothesis, which Lean cannot discharge for T-count because the T-count model is not formalized.

The barriers are conditional and not hardness results. They do not put the problem in P. The two open blocks are the questions they leave: Lean has no statement about the KMY points fixed, or about T-count, beyond the conditional.

NP-hardness when the points are supplied

If the interpolation points are part of the input, the structural-score problem is NP-hard already at arity 2. The reduction composes three steps, each an equivalence proved in Lean: a satisfiable formula becomes a digraph of out-degree at most 2 with a Hamiltonian cycle, that becomes a Hamiltonian cycle in a line graph, and that becomes a table instance whose cheap schedules are exactly such cycles. The map is polynomial-time on complexitylib's machines. The figure is drawn in dependency order, from the lemmas the composition rests on at the top to the theorem at the bottom, so the reduction itself runs against the arrows.

It is a result about the structural score \(S=A+5L\) with supplied points. It is not a statement about T-count, not about the KMY points, and not about the problem where the policy chooses the points, which the barrier makes NP-hardness of unlikely. What it shows is that the ordering of the points alone carries combinatorial difficulty.

Checking it yourself

Each Lake project builds on its own. With elan installed, and about 16 GB of RAM for the first (do not run the two builds at once): 

cd efficient_tables
lake exe cache get                          # prebuilt Mathlib oleans, pinned revision
lake build EfficientTables EfficientTablesHelpers
lake env lean scripts/AxiomAudit.lean       # #print axioms on the headline theorems

cd lean_hardness                            # separate project, separate toolchain
lake build                                  # compiles ~2.3k complexitylib modules, ~20 min
lake env lean Mahaney/Audit.lean
lake env lean Points/Audit4.lean

The Fortran solver needs only a GNU Fortran compiler and Python 3 (the reference build used GNU Fortran 16.2.0; build.py reads FC, --compiler, or gfortran on the path), and builds independently of both Lake projects: 

cd efficient_tables/fortran/phaseproduct_saturation_f90
python -B build.py --debug
python -B tests/test_solver.py build/debug/phaseproduct_saturation   # replay + cost checks on the executable
python -B tests/test_frontend.py                                      # outer stage vs. independent enumeration
python -B tests/test_backend.py                                       # ILP and lattice vs. brute force
python -B tests/test_local.py                                         # oracle and threshold vs. Python witness
python -B tests/audit_f90.py                                          # Fortran 90 subset guard

The full procedure, with the expected costs, is in REPRODUCING.md. The proof map is regenerated with python3 efficient_tables/scripts/gen_docs_graph.py --check, and the data of the two figures above with python3 efficient_tables/scripts/gen_suite_data.py --check, which fails if a quoted line, a count, or a Fortran use edge no longer matches the sources.
